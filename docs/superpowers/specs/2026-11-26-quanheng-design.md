# 权衡 Quanheng：总体设计与第一阶段设计

- 日期：2026-11-26
- 状态：待确认
- 范围：整体架构，以及第一阶段"选择模型跑通全流程"的详细设计。时机模型和分配模型在本文只给出概要，轮到时各写一份短设计。

标注约定：没有特别标注的内容来自项目发起人的明确决定；标了 **〔我的决定〕** 的是设计者替发起人做的选择，可以推翻。

## 1. 意图

把生活里的决策（尤其是"二选一"）变成可以复算的公式，让结论来自计算而不是来自语言模型的即兴发挥。

**为什么做**：发起人不想被 LLM 的幻觉建议影响决策。直接问 LLM"我该选哪个"，得到的是一段听起来有道理、但无法验证的话。这个项目要把"听起来有道理"换成"可以检查每一步"。

**一句话原则**：LLM 只做翻译，数字和结论全部由确定性代码产生。

## 2. 成功与失败

**置信度的定义**：置信度就是稳健度。每个不确定的输入用范围而不是单个数字表示；抽样一万次，看结论在多少比例的情况下不变。例如"A 在 93% 的情况下胜出"。

这个数字的含义是"在你给出的范围和偏好之内，结论有多稳"。它不是"事后证明选对了"的概率，界面上必须把这句话说清楚。

**成功**
- 每个结论都带一个可以复算的稳健度。
- 稳健度低的时候，明确指出哪个输入一变结论就翻转，以及补上哪条信息最能提高它。

**失败（即使程序能跑）**
- 给出了没有计算依据的高置信度。
- 置信度低，却不说原因。

为了显得可信而总是输出高置信度，是另一种幻觉。两个选项本来就接近时，诚实的答案就是"差不多，取决于某个因素"。

## 3. 目标、非目标、反目标

### 目标（第一版）

1. 三类决策模型：多准则选择、不确定性下的时机、约束下的分配。每类只做一个最朴素的模型，按这个顺序实现。
2. 三类模型共用一套"带来源的不确定数值"和稳健度计算。
3. 自然语言输入：LLM 判断问题属于哪一类，并把文字填进对应的模板。
4. 每个进入计算的数字都有来源标注。
5. "如果……会怎样"：改参数、重算、对比前后结果。
6. 不配置 LLM 也能用：手动填表即可完成全部计算。
7. Python 引擎加本地 Web 界面。界面中文，README 中英双语。

### 非目标（第一版不做）

- 规则引擎（Zen）、低代码编排（Dify、n8n）
- 桌面安装包（以后在 Web 界面外面套壳）
- 账号、多用户、云端托管、多人共同决策
- 自动联网取数（机票价格接口、网页抓取）
- 大量 MCDA 算法（TOPSIS、VIKOR、PROMETHEE 等）
- 多阶段的最优停止问题（时机模型第一版只比较"现在"和"等到某个时点"）
- 投资组合优化（Riskfolio、PyPortfolioOpt）
- 英文界面（但文案从第一天起集中存放，方便以后加）

### 反目标（出现就算失败）

- **虚假的置信度**：任何不是算出来的置信度数字或措辞。
- **没有来源的数字**进入计算。
- **LLM 改动数字或结论措辞**。
- **结果不可复算**：同一个模型、同一个随机种子、同一个引擎版本，必须得到相同的结果（范围见 7.3）。
- **把主观偏好伪装成客观**：权重是使用者的偏好，界面必须如实呈现这一点。
- **推荐具体金融产品**：投资回报的分布是使用者自己填的假设，工具只在这些假设上做计算。

## 4. 约束

- 本地优先：服务只监听 `127.0.0.1`，决策数据只存在本机。
- 使用者自带密钥，接入 OpenAI 兼容接口，客户端留出可替换的接口。
- 数据只在使用者主动触发某个 LLM 功能时才发出，只发给他们自己配置的服务商，只发完成该功能所需的内容（见 8.6）。没有任何自动的后台发送。
- 支持 Windows、macOS、Linux。
- 许可证 MIT。新增依赖必须是宽松许可证（MIT、BSD、Apache）。
- 优先考虑长期维护和后续加功能的难度，而不是最快出第一版。
- 没有规定的交付日期，按长期维护项目推进。

## 5. 考虑过的搭法

| | 做法 | 好处 | 代价 |
|---|---|---|---|
| **A（采用）** | 模板库 + 普通代码串流程。三类决策各有一个人写的模型模板，LLM 只填模板和讲解结果 | 每条公式都是人写的、有测试的；引擎不依赖 LLM；依赖最少 | 只能处理套得进模板的问题；新增一类要写新模板 |
| B | LangGraph 状态机。模板相同，流程画成状态图 | 自带断点续跑和人工确认；贡献者熟悉 | 依赖重、接口变动频繁；我们的流程很短，"循环"就是使用者在界面上改表单，状态图帮不上多少 |
| C | LLM 现写求解代码（OptiGuide 的做法） | 什么问题都能接 | 公式本身成了 LLM 的输出，写错的目标函数藏在正规的数学后面，是最危险的幻觉；需要沙箱；不可复算 |

**选择 A 的原因**：发起人把技术选型交给了设计者，要求是好维护、好扩展、不被幻觉影响。A 是唯一让"公式由人写"这件事成立的搭法。

**从 C 借来的一点**：假设追问翻译成"参数修改"而不是代码，算术由代码完成（见 7.4）。

**给 B 留的门**：引擎和流程层是分开的。以后流程变成多步、长时间运行时，可以把流程层换成 LangGraph 而不动引擎。

## 6. 总体架构

```
            ┌──────────────── 浏览器（React + TypeScript）────────────────┐
            │  描述决策 → 确认模型 → 设定权重 → 看结果 → 假设追问          │
            └───────────────────────────┬───────────────────────────────┘
                                        │ HTTP，仅 127.0.0.1
            ┌───────────────────────────┴───────────────────────────────┐
            │                    服务层（FastAPI）                        │
            │   纯计算接口（不碰 LLM）   │   LLM 接口   │   本地存储      │
            └──────────┬────────────────┴──────┬───────┴────────────────┘
                       │                       │
        ┌──────────────┴─────────────┐   ┌─────┴──────────────────────┐
        │  引擎（纯数学，无网络）       │   │  LLM 层                     │
        │  数值与来源 / 三类模型 /      │   │  起草模型 / 翻译假设 /       │
        │  抽样、稳健度、翻盘点         │   │  讲解结果，各带一道代码防线   │
        └────────────────────────────┘   └────────────────────────────┘
```

**依赖方向是单向的**：引擎不导入 LLM 层和服务层的任何东西。这条规则要有自动检查（测试或 lint 规则），否则迟早会被打破。

引擎可以单独使用：在 Python 里直接调用，或用命令行对一个决策文件求解。

## 7. 核心概念

### 7.1 带来源的不确定数值

引擎里每个输入数字都是这样一个对象：

- **取值**，三种写法之一：
  - 确定值（一个数）
  - 范围（最低、最高）
  - 三点估计（最低、最可能、最高）
- **单位**（如"日元/月""分钟"）
- **来源**，四种之一：
  - `user_input`：使用者手填
  - `quoted`：出自使用者提供的文字，必须附带原句
  - `imported`：来自导入的文件，附带文件名和位置
  - `llm_inferred`：LLM 推测，附带推测理由
- **是否已确认**

**硬规则**：凡是经过 LLM 的数值（`quoted` 和 `llm_inferred`），只要还有一个未确认，引擎就拒绝计算。这个检查放在引擎的入口，而不只是界面上，这样命令行和接口调用也绕不过去。

`quoted` 也要确认的原因：代码能检查原句确实存在，但检查不了 LLM 从原句里读出的数字对不对（例如把"7 万"读成 80000，或者换算错单位）。

确认的方式：
- `llm_inferred`：逐个确认，或者改成自己认可的值或范围（此时来源变为 `user_input`）。
- `quoted`：数值和原句并排显示，可以看完后一次性全部确认。

**〔我的决定〕** 范围按均匀分布抽样，三点估计按三角分布抽样。不确定输入之间假设相互独立，这条假设要显示在结果里。

### 7.2 三类决策模型

所有模型共用一个外壳：类型标记、模式版本号、标题、原始描述文字。可以整个存成一个 JSON 文件，拿到别的机器上能重算（精确到什么程度见 7.3）。

| 类型 | 回答的问题 | 例子 | 阶段 |
|---|---|---|---|
| 选择 | 几个候选里哪个最符合我的偏好 | 两套房子租哪套 | 第一阶段，见第 8 节 |
| 时机 | 现在做，还是等一等 | 机票现在买还是再等 | 第二阶段，见 9.1 |
| 分配 | 有限的资源怎么分 | 月度预算怎么分 | 第三阶段，见 9.2 |

### 7.3 稳健度的计算

三类模型共用同一套做法：

1. 对每个不确定的输入抽样，默认 10,000 次。
2. 每次抽样都完整算一遍模型，记下这一次的结局。
3. 统计结局的分布。

**每次抽样的结局**只有三种，三种的比例加起来是 100%：
- 某个候选单独胜出；
- 几个候选并列第一，这一次平分给并列者；
- 没有任何候选可行（见 8.3）。

**复算的范围**〔我的决定〕
- 随机种子、抽样次数、引擎版本、NumPy 版本都写进结果里。
- 同一平台、同一引擎版本、同一份锁定的依赖：结果逐字节相同。
- 跨操作系统或处理器：不保证逐字节相同，但所有显示出来的数字和结论措辞必须一致。持续集成在三个操作系统上用同一批决策文件验证这一点。
- 不追求跨平台逐字节相同，因为那需要自己重写抽样器并禁用底层数学库，代价与收益不相称。

**每个输入有自己的随机流**：由种子和该输入的标识共同决定，并且先抽"分位"再换算成数值。这样修改一个输入时，其他输入抽到的值完全不变；把一个范围改成另一个范围时，它在每次抽样里仍处在相同的分位上。假设追问的前后对比依赖这一点（见 7.4）。

**其他要求**
- 稳健度自己也有抽样误差，要一起显示（10,000 次时约为 ±1%）。
- **结论措辞由代码按阈值决定**，LLM 不能改。〔我的决定〕默认阈值如下，可配置：

| 情况 | 措辞 |
|---|---|
| 最高的胜出率 ≥ 90% | 明确 |
| 70%–90% | 倾向 |
| 低于 70% | 难分高下 |
| "没有任何候选可行"是占比最大的结局 | 多数情况下没有可行方案 |

"没有任何候选可行"的比例只要不为零，就要在结论旁边显示。

### 7.4 假设追问

一次假设追问就是对模型的一组修改，每条修改包含：

- 目标：模型里的哪个数值
- 操作：设为、乘以、加上
- 数值

可以修改的目标：分数表里的数值、权重、硬约束的门槛。锚点不在其中，原因见 8.2。

代码执行修改，展示"A 的房租：7.0 万 → 8.4 万"，然后用**同一个随机种子**重算。因为每个输入有自己的随机流（见 7.3），没被修改的输入在前后两次计算里抽到的值完全相同，差异只来自修改本身。输出是前后对比：胜出率变化、结论是否翻转。

使用者可以直接在表单上改，也可以用自然语言问。后一种情况下 LLM 只负责把问题翻译成上面的修改清单，乘除加减由代码做。

## 8. 第一阶段：选择模型

### 8.1 模型里有什么

- **候选**：至少两个，每个有名称和备注。
- **准则**：每条有名称、单位、两个锚点。
  - **锚点**是使用者设定的两个参照值："差"和"好"。例如房租：差是 9 万，好是 5 万。
  - 数值按锚点线性换算成分数："差"对应 0，"好"对应 1。
  - 超出锚点的数值按同一条直线外推，分数可以低于 0 或高于 1，并提示使用者"这个值超出了你设的参照范围"。不截断，否则 9 万和 20 万会被当成一样差。
  - 〔我的决定〕每条准则可以单独打开"超过'好'之后不再加分"，默认关闭。
  - 没有天然数值的准则（如"采光""喜欢程度"）直接打 0–10 分，同样可以给范围。
- **硬约束**：某条准则必须满足的门槛。不满足的候选被淘汰。
- **分数表**：每个候选在每条准则上的数值，都是 7.1 里那种带来源的数值。
- **权重**：每条准则一个，合计为 1。

**为什么用锚点而不是按候选之间的最大最小值归一化**：只有两个候选时，按最大最小值归一化会让每条准则都变成一个得 1 分、一个得 0 分。房租差 100 日元和差 5 万日元会被当成一样大的差距。锚点让"差多少"保留了下来。

锚点还有第二个作用：它定义了设定权重时拿来比较的"变化幅度"（见 8.2）。

### 8.2 权重怎么来

权重是使用者的偏好，不能由 LLM 给出，也不能用熵权法之类的方法从数据里算。

- **主要方式：两两比较**。每次问一对准则，而且问的是具体的变化幅度："房租从 9 万降到 5 万"和"通勤从 60 分钟降到 20 分钟"，哪个对你更重要，重要多少。用标准的层次分析法数学把比较结果换算成权重，并给出一致性指标。
- **快捷方式：直接打分**。给每条准则的变化幅度打 0–100 分，归一化后得到权重。
- 一致性差时提示使用者，并指出最矛盾的那一对。
- **权重本身也是不确定的**。〔我的决定〕提供一个三档的"我对这些权重有多确定"选项，默认中间档；抽样时权重围绕中心值波动，档位越不确定波动越大，一致性差时进一步放大波动。波动必须是按比例的：每条权重各自乘以一个随机系数，再归一化。

准则数量建议不超过 7 条，否则两两比较的次数太多。

**改了锚点怎么办**：权重描述的是"这条准则从差到好"有多重要，所以它和锚点绑在一起。使用者真正稳定的偏好是换算比例（例如"通勤少 1 分钟值多少日元"）。〔我的决定〕锚点被修改时，代码自动换算该准则的权重，保持这个比例不变，并告诉使用者"权重已按新的参照范围换算"。

在没有打开"不再加分"的情况下，这样换算后每次抽样的胜出者都不变，所以胜出率完全相同。这依赖上面"波动按比例"的要求，并且要有测试。正因为改锚点不改变结论，锚点不作为假设追问的目标。

### 8.3 计算

- 候选的总分 = 各准则的权重 × 换算后的分数，求和。
- 硬约束在**每次抽样里**单独判断。一个候选在某次抽样里不满足约束，这次就不能胜出。所以结果里会有"A 有 30% 的情况会超出预算"这样的信息。
- 某次抽样里总分并列第一的候选平分这一次。分数来自有限的几个固定值时，并列并不罕见。
- 某次抽样里所有候选都不满足约束，这一次记为"没有任何候选可行"，不算任何人胜出。
- "没有任何候选可行"是占比最大的结局时，不硬给答案，而是报告每条约束离最近的候选差多少（用中心值算），告诉使用者放宽哪一条最容易得到可行方案。

### 8.4 输出

| 输出 | 内容 |
|---|---|
| 结论 | 措辞档位、胜出者、胜出率及其抽样误差 |
| 可行性 | 每个候选满足全部硬约束的比例 |
| 贡献拆解 | 用中心值算出的总分，以及每条准则各贡献了多少 |
| 分差分布 | 胜出者与第二名的分差，只统计两者都可行的抽样，并注明用了多少比例的抽样；给出 5%、50%、95% 分位和直方图 |
| 翻盘点 | 逐个输入来看，这个输入变到多少结论会翻转。定义见下 |
| 最值得补的信息 | 把不确定的输入按"弄准它能消除多少结论的不确定"排序 |
| 假设清单 | 这次计算依赖的假设（输入相互独立、分数线性换算等） |

**翻盘点的定义**：把某一个输入固定在一个值上，其余输入保持各自的范围照常抽样，重新统计胜出率。让"胜出率最高的候选"换人的那个临界值就是翻盘点。它和结论用的是同一个判据，所以"把输入改到翻盘点之外，结论确实换人"是可以测试的。

- 分数表里的数值：在该准则的两个锚点之间找。
- 权重：在 0 到 1 之间找，其余权重按比例缩放，保持合计为 1。
- 找不到临界值时，输出"在参照范围内，这个输入怎么变都不会翻转结论"。这是一个有效的、有信息量的输出。
- 落在使用者所填范围内的翻盘点排在最前面。

**贡献拆解是用中心值算的**，只用来解释"为什么"。少数情况下中心值的排名会和抽样得出的胜出者不一致（例如输入的范围很偏），此时要明确提示，并以抽样结果为准。

### 8.5 界面

三步走：

1. **描述或手建**：一个文本框写下决策，或者选择手动新建。
2. **确认模型**：一张可编辑的表。每个数值旁边有来源标记，`quoted` 的和原句并排显示，`llm_inferred` 的高亮显示；还有未确认的数值时"计算"按钮不可用。接着是权重设定。
3. **结果**（下图是示意，数字仅为举例，不是算出来的）：

```
┌──────────────────────────────────────────────────────────────┐
│ 租 A 还是租 B？                                                │
│                                                              │
│ 倾向 A          A 在 84% 的情况下胜出（±0.7%）                  │
│ 在你给出的范围和偏好之内成立，不代表事后一定更好                   │
│                                                              │
│ 为什么是 A      [各准则贡献的条形图]                             │
│                 通勤 +0.21   房租 −0.08   采光 +0.05            │
│                                                              │
│ 什么会让结论翻转                                                │
│   · B 的通勤时间低于 31 分钟（你填的是 35–50）                   │
│   · "房租"的权重高于 0.46（现在是 0.30）                         │
│                                                              │
│ 最值得补的信息                                                  │
│   1. B 的实际通勤时间（现在是推测的范围）                         │
│   2. A 的管理费                                                │
│                                                              │
│ 这次计算的假设  ▸                                               │
│                                                              │
│ 如果……会怎样？ [ A 的房租涨 20%                ] [对比]          │
└──────────────────────────────────────────────────────────────┘
```

### 8.6 LLM 的三个任务，以及各自的代码防线

| 任务 | LLM 做什么 | 代码防线 |
|---|---|---|
| 起草模型 | 判断决策类型；列出候选、准则、建议的锚点；从文字里抽取数值 | 输出必须通过模型模板的校验，失败则带着错误信息重试，再失败就让使用者手填。标为 `quoted` 的数值，其原句必须能在使用者的文字里逐字找到，找不到就降级为 `llm_inferred`；找到了也仍需使用者确认（见 7.1）。LLM 建议的锚点一律算 `llm_inferred`。LLM 不产出权重 |
| 翻译假设 | 把"如果 A 的房租涨 20%"翻译成修改清单 | 修改清单必须通过校验；目标必须是模型里真实存在的数值；执行前向使用者展示修改前后的值 |
| 讲解结果 | 在代码生成的结论句之后，补一段通顺的说明 | 结论句（谁胜出、胜出率、措辞档位）永远由代码模板生成并显示在最前面，LLM 改不了。LLM 的补充说明里不允许直接写数字，只能用占位符引用计算结果里的字段，由代码填入。出现任何直接写出的数字或不存在的占位符，整段丢弃 |

**模板生成的讲解永远存在**，LLM 的讲解只是可选的补充。所以没有 LLM 时功能是完整的。

**每个任务发给 LLM 什么**
- 起草模型：使用者写下的那段文字。
- 翻译假设：使用者的问题，加上模型里候选和准则的名称、当前数值。
- 讲解结果：候选和准则的名称、计算结果。

三个任务都只在使用者点击对应按钮时触发。〔我的决定〕LLM 讲解默认不自动生成，设置里可以改成每次计算后自动生成。

文字套不进任何一类模板时，如实告诉使用者，并提供手动新建，不要硬套。

## 9. 后续阶段（概要）

这两节只说明意图和大致形状，确保架构容得下它们。细节在轮到时单独设计。

### 9.1 时机模型（第二阶段）

回答"现在做，还是等到某个时点"。输入包括：现在的价格；到那个时点价格下降、上涨的概率和幅度；买不到的概率；计划有变的概率和届时的损失（如退改费）。

输出：两种做法的期望成本、"等更划算"的比例、翻盘点（如"降价概率要高于 38% 等才划算"）。

需要提前接受的限制：没有历史价格数据时，降价概率只能是使用者的主观估计。工具照实标注来源，这类结论的稳健度会因此偏低。

### 9.2 分配模型（第三阶段）

回答"有限的资源怎么分"。每个类别有下限、上限和一条边际效用递减的曲线，在总量约束下求总效用最大的分法。

有些类别不是能随意调的数字。例如房租取决于选哪套房，交通费又跟着房子走。所以实际形状是"先在几个离散选项里选，再分配剩下的"。

输出不是单个胜出率，而是每个类别的建议区间（如"房租 6.5–7.2 万"）。效用曲线是这类模型里最主观的部分，界面要如实说明。

### 9.3 文件导入（第四阶段）

〔我的决定〕第一阶段只支持手动填表和粘贴文字。之后先做 CSV 和 Excel 表格导入（行是候选，列是准则，带列映射步骤）；PDF、网页等其他格式走"提取文字后交给 LLM 起草"这条路。

## 10. 技术选型〔全部是我的决定〕

| 部分 | 选择 | 理由 |
|---|---|---|
| 引擎 | Python ≥ 3.11，NumPy、SciPy、Pydantic v2 | 科学计算生态最成熟；Pydantic 模板可直接导出 JSON Schema |
| 包管理 | uv | 快，锁文件可复现 |
| 服务 | FastAPI | 类型即接口文档，可生成前端类型 |
| 前端 | React + TypeScript + Vite | 生态最大、最好招贡献者；以后套桌面壳（如 Tauri）可直接复用 |
| 前后端类型同步 | 从接口描述自动生成 TypeScript 类型 | 避免两边手写两份 |
| LLM 客户端 | OpenAI 兼容的对话接口，地址、密钥、模型名可配 | 兼容面最广，本地模型也能接 |
| 存储 | 本机用户数据目录下的 JSON 文件 | 简单、可对比、可携带 |
| 质量工具 | ruff、类型检查、pytest；前端 lint 和测试；GitHub Actions | 长期维护的底线 |
| 分发 | 前端构建产物打进 Python 包，一条命令启动服务并打开浏览器 | 使用者不需要装 Node |

不用纯 Python 界面框架（Streamlit、Gradio）的原因：带来源标记和范围编辑的表格在这类框架里很别扭，而且以后套桌面壳需要一个真正的 Web 前端。

## 11. 怎么验证它是对的

这个项目的全部价值在于"算得对、说得准"，所以验证是设计的一部分。

**引擎**
- 手算过的小例子作为单元测试。
- 性质测试：
  - 一个候选在所有抽样里每条准则都严格优于另一个，且始终可行，胜出率必须是 100%。
  - 两个完全相同的候选，胜出率各为 50%（并列平分）。
  - 各候选的胜出率加上"没有任何候选可行"的比例，等于 100%。
  - 同一平台上，同样的模型和种子，结果逐字节相同；三个操作系统上，显示的数字和结论一致。
  - 把某个输入固定到它的翻盘点之外，胜出率最高的候选确实换人。
  - 修改一个输入后，其他输入在每次抽样里的取值不变。
  - 修改锚点并自动换算权重后，每次抽样的胜出者不变（未打开"不再加分"时）。
  - 存在未确认的 `quoted` 或 `llm_inferred` 数值时，引擎拒绝计算。
- `examples/` 里放几个完整的决策文件，同时作为回归测试和文档。

**LLM 层**
- 持续集成里不调用真实的 LLM，用录制的或手写的响应。
- 专门测试三道防线：原句找不到时降级、讲解里直接写出数字时被丢弃、修改清单指向不存在的数值时被拒绝。

**服务层**
- 纯计算接口在没有配置 LLM 时全部可用。

## 13. 留给实现者决定的事

- 包内部的模块划分；是否把引擎和服务拆成两个发行包。
- 层次分析法用特征向量法还是几何平均法。
- 权重波动的具体分布和三档对应的参数（必须是按比例的波动，见 8.2）。
- 翻盘点的搜索方法。要求：复用同一批抽样，不为每个输入重新抽样。
- "最值得补的信息"的具体估计方法。要求：复用同一批抽样、给定种子结果确定、有合理性测试。
- 结构化输出的实现方式（服务商原生的 JSON 模式，或提示词加校验重试）。
- 密钥的保存方式。要求：不进决策文件、不进日志、不放在浏览器存储里、只发往使用者配置的地址。
- 防止其他网页调用本地接口的机制（来源检查、令牌等）。要求：必须有。
- 图表库和组件库。
- 接口的具体路径和决策文件的字段命名。
- 抽样的性能优化。

## 14. 独立审阅后补上的决定

独立审阅没有留下必须由发起人回答的问题。下面这些是审阅指出、由设计者补上的决定，都已写进正文，都可以推翻：

1. 经过 LLM 的数值一律要确认，包括附带原句的（7.1）。
2. 复算的范围：同平台逐字节相同，跨平台显示一致（7.3）。
3. 每个输入有自己的随机流，保证假设追问的前后对比干净（7.3、7.4）。
4. 并列平分；"没有任何候选可行"是单独的一种结局，有自己的措辞档位（7.3、8.3）。
5. 锚点之外线性外推，不截断（8.1）。
6. 改锚点时自动换算权重；锚点不作为假设追问的目标（8.2）。
7. 翻盘点和结论用同一个判据（8.4）。
8. 结论句永远由代码生成；LLM 的讲解不能直接写数字（8.6）。
9. LLM 功能只在点击时触发，讲解默认不自动生成（4、8.6）。
